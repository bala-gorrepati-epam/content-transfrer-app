# Content transfer SDK guide

Source of truth is `types.gen.d.ts` in `@sitecore-marketplace-sdk/xmc` (namespace `ContentTransfer`).
If this skill disagrees with the installed types, the installed types win.

## How to use this skill
1. Use the flow table and rules below to plan the code.
2. Before writing any call, read `references/operations.md` for the exact params, response shape
   and example of that operation. Read only the sections you need.
3. Never guess param names, casing or which environment a call targets.

## Conventions
- Operation names: `xmc.contentTransfer.<operation>`.
- Every operation takes `sitecoreContextId` in `query`. Always pass it explicitly.
- SOURCE = environment items are copied from. DESTINATION = environment items are written to.
- Assumed request shape (CONFIRM against the client package types): `client.mutate("<operation>", { params: { path?, query?, body? } })`.
- Some operations are GET endpoints (status, getChunk, getBlobState). CONFIRM whether the SDK
  exposes them through `client.mutate` or `client.query`, and update this skill once known.
- Response casing is inconsistent in the API. Use the exact casing shown in the reference.

## Flow and data passed between steps

| Step | Operation | Environment | Needs | Produces |
|------|-----------|-------------|-------|----------|
| 1 | createContentTransfer | SOURCE | `transferId` (generated by us), dataTrees | 202, no body |
| 2 | getContentTransferStatus | SOURCE | `transferId` | `State`, `ChunkSetsMetadata[]` |
| 3 | getChunk | SOURCE | `transferId`, `chunksetId`, `chunkId` | `Blob` |
| 4 | saveChunk | DESTINATION | same ids as step 3, the `Blob` | 201, no body |
| 5 | completeChunkSetTransfer | DESTINATION | `transferId`, `chunksetId` | `ContentTransferFileName` |
| 6 | consumeFile | DESTINATION | `databaseName`, `fileName` | 202, no body |
| 7 | getBlobState | DESTINATION | `fileName` | `status`, `details` |
| 8 | deleteContentTransfer | SOURCE | `transferId` | 202, no body |

## Rules
- Generate `transferId` once per run with `crypto.randomUUID()`. Reuse it in steps 1 to 5 and 8.
- `chunksetId` values come from `ChunkSetsMetadata[].ChunkSetId` (step 2).
- Loop `chunkId` (a number) over each chunk set's `ChunkCount`. Fetch from the source (3), save to the destination (4), same ids on both.
- Do not call getChunk until step 2 reports `State` as `Completed`.
- Call step 5 once per chunk set, after all its chunks are saved. Keep every returned `ContentTransferFileName`.
- Steps 6 and 7 use that file name. 202 responses mean the work is asynchronous, so poll (step 2 for create, step 7 for consume).
- Always run step 8, also when an earlier step fails, so source transfers are not left behind.
- Keep chunk data as a `Blob` end to end. Never convert it to text or JSON.
- dataTrees fields (`itemPath`, `scope`, `mergeStrategy`) are optional in the types but must be required in our own wrapper types.
- Scope values: `SingleItem`, `ItemAndDescendants`.
- MergeStrategy values: `OverrideExistingItem`, `KeepExistingItem`, `LatestWin`, `OverrideExistingTree`. There is no `SkipIfExist`.
- Never log bearer tokens or context IDs.

## Unverified, check on the first real run against a test environment
1. The request wrapper shape and query-vs-mutation exposure (see Conventions).
2. Whether chunk ids start at 0 or 1.
3. Whether the client returns the `getChunk` body as an intact `Blob` (check `blob.size > 0`).
4. How to know when a chunk is media (`isMedia` on saveChunk). Leave it unset until known.
5. Whether `ContentTransferFileName` is already the full path `consumeFile` expects.
6. What `getBlobState` statuses (`OK`, `NotFound`, `Error`) mean while a file is still being consumed.
7. The names of transfer states other than `Completed`, including a failed state.
Log the raw outputs of these on first runs, then update this skill with what is confirmed.

## Not covered
- `xmc.authoring.graphql` (item tree browsing). Extract its types separately.

## Open decisions
- Poll interval and timeout for steps 2 and 7.
- Sequential or parallel chunk transfer (start sequential).
- Retry policy for a failed chunk.
- Language and version handling for copied items.
